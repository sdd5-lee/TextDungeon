# 2단계 결과 요약 (2026-10-29)

계획서 v3.1의 2단계(프롬프트 축소, 보상 요약). 확인은 에뮬레이터(`TextDungeon_LLM`, CPU, Gemma 4 E2B)에서 했다.

## 2-1. 프롬프트 줄이기

0-A 때 대부분 해 두었다 (아이템 후보 5개, 괄호 안내문 대신 예시 1개, `validItemIds`를 후보 5개로 한정, 클라우드도 같은 프롬프트).
이번에는 보상설명에서 수치를 빼면서 예시와 규칙이 조금 더 짧아졌다.

| 항목 | 0-A 최종 | 2단계 |
| --- | --- | --- |
| 프롬프트 길이 | 597~662자 | 589~654자 |
| 형식 성공 (20건) | 20/20 | **20/20** |
| 응답 시간 중앙값 (에뮬레이터 CPU) | 4.5초 | 3.2초 (느린 쪽 10% 3.7초) |

- 600자를 넘는 건 이벤트의 "상황" 문장이 긴 경우다. 지시문 자체는 600자보다 훨씬 짧다. 더 줄이려면 0-A에서 넣은 교정 문구("현재 값이 아니라 늘거나 준 양", "적에게 준 피해는 적지 않는다")를 빼야 해서 그대로 두었다
- 첫 건이 8.1초 걸렸다. 에뮬레이터를 막 켠 뒤에만 그렇고(같은 조건 다시 켠 직후 1회 재현, 앱만 다시 켰을 때는 4.1초) 모델 파일을 디스크에서 처음 읽는 시간으로 보인다. GPU는 초기화 때 가중치를 올리므로 0-B에서 실기기로 확인한다

## 2-2. 보상설명과 실제 수치 일치

- 프롬프트: "보상설명은 결과를 묘사하는 문장이고 숫자는 쓰지 않는다. 스탯 줄은 그 묘사와 맞게…". 예시 보상설명에서도 수치를 뺐다
- 코드가 요약을 붙인다: `Reward.summary(rewardMultiplier, expMultiplier, itemName)` → `… 정신이 맑아지지만, 이내 낯선 환영에 시달린다. (지혜 +6, HP -10, 나무 검 ×2)`
  - 경험치 = 층 상한 적용 값 × 난이도 배수 × 특성 경험치 배수 / 그 외 = 층 상한 적용 값 × 난이도 배수 / 아이템 = 이름 ×난이도 배수 (1이면 이름만)
  - HP 변화는 `HP +N`(회복), `HP -N`(피해)로 보여 준다
  - 특성 배수는 `Reward.expMultiplier(player)` 하나를 `Reward.apply()`와 같이 쓴다
- `requestChaosChoice`가 난이도 배수와 특성 경험치 배수를 받는다 (`EventActivity`에서 넘김)
- 데이터에 있는 기존 이벤트 설명은 건드리지 않았다

결과: 보상설명에 숫자가 들어간 응답 **0/20** (이전 프롬프트는 20/20이 수치를 붙였고 그중 2~3건이 스탯 줄과 달랐다).

## 2단계 완료 기준

| 상황 | 결과 |
| --- | --- |
| 줄인 프롬프트로 테스트 20개 | 통과. 20/20 |
| 모험의 축복 + 어려움에서 경험치 보상 | 통과 (단위 테스트). 경험치 10 → 요약 "경험치 +60", 실제 증가 60 |
| 아이템 보상 + 보통 난이도 | 통과 (단위 테스트). 요약 "나무 검 ×2", 실제로 2개 받음 |

단위 테스트 `RewardSummaryTest` 5개 추가, 전체 164개 통과.

## 확인할 것 (사용자 판단)

- **아이템을 거의 매번 준다**: 20건 중 19건이 아이템을 골랐다. 보통 난이도면 주사위 한 번에 아이템 2개다. 프롬프트로 줄이거나(예: "아이템은 드물게"), 코드에서 일정 확률로만 남기는 방법이 있다
- 묘사와 스탯이 느슨하게 맞는 응답이 몇 건 있다 (예: 통로가 열리는 묘사에 "민첩 -1"). 수치가 묘사에 없으니 예전처럼 문장과 숫자가 정면으로 어긋나지는 않는다
